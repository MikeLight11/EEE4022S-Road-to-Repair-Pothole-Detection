# Web app brain dump

The issue: the device in the car can detect and measure a pothole and tag it with GPS, but on its own that data just sits on a Pi. The city needs to see where the potholes are, send crews to fix them and know they were actually fixed. So the web app is the other half of the system: the device uploads detections, the admin sees them on a map, groups them into jobs by suburb, shares each job with a crew by link, and the crew marks each pothole filled (or not a pothole) with a photo. Only Cape Town for now.

Requirements it must solve: the device needs a simple authenticated way to upload (API key, no login) and retries must not create duplicates. The same pothole gets detected every time the car drives past, so repeat detections must be dropped, but two real potholes can be right next to each other. The admin needs a map, filters, a way to make jobs and a material estimate. Crews shouldn't need accounts, so jobs are shared by an unguessable link, and the crew page must work well on a phone. The city needs proof of repairs (photo + phone GPS) and a history for when someone complains a pothole wasn't fixed.

Built with Flask (Python), SQLite as the database (one file, data/potholes.db) accessed through Flask-SQLAlchemy, which means it could be switched to MySQL/Postgres by changing DATABASE_URL. Maps use Leaflet with OpenStreetMap-based CARTO tiles and marker clustering. Plain HTML/CSS/JS, no build step, run with `python app.py`.

Suburbs: the device only sends GPS, but jobs are per suburb. Instead of a paid/rate-limited geocoding API, the server looks the suburb up offline using the City of Cape Town's Official Planning Suburbs dataset (778 suburbs, simplified from 8.5 MB to about 738 KB) with a point-in-polygon test. Points just outside a boundary (roads often are the boundary) get the nearest suburb within 150 m.

Features:
- Upload API: validates everything, checks the image is a real JPEG/PNG, works out suburb and severity. Severity is from area: ≥0.5 m² critical, ≥0.25 high, ≥0.1 medium, else low (my own thresholds, need to justify).
- Duplicates: dropped if within 10 m of an unfilled pothole and captured at least 5 min apart. The time rule keeps neighbouring potholes seen seconds apart on the same pass. Uses capture time, not upload time, so late batch uploads still work.
- Job Creator Map: filters, job status/severity views, filled potholes hidden, clustering. "+ Create a job" lets the admin click suburbs and see counts and asphalt per suburb. The server claims all unassigned, unfilled potholes in those suburbs in one database update, so a pothole can never end up in two jobs.
- Asphalt estimate: potholes are repaired by cutting out a rectangle in 0.25 m steps, so the pothole keeps its measured size but materials use the cut (each side rounded up to the next 0.25 m, e.g. 0.79 × 1.11 m → 1.00 × 1.25 m cut). Asphalt = cut area × 50 mm depth × 2400 kg/m³ × 1.1 wastage (assumptions, need to fact check). Potholes marked "not a pothole" don't count.
- Sidebar: open and completed jobs with potholes left and time open/time taken. Complete = no unfilled potholes left (worked out, not stored).
- Admin job page: that job's potholes with the suburbs outlined, progress view, copy job link, and admin can mark "not a pothole" with a reason (no photo).
- Job link (/j/random-token, no login): stats, map and list of potholes to repair. Mark filled or not a pothole (with reason), photo required, phone GPS and distance to the pothole recorded. Locked once marked. Google Maps navigation. Built mobile-first (full-screen map, bottom sheets, my location). "Job complete" popup.
- Status history: every change with who (crew/admin), when, reason, crew distance from pothole and before/after photos. Photos are never deleted.
- Find a pothole: search by ID, address (OpenStreetMap Nominatim, about 1 request/sec limit, need to check policy) or clicking the map, and list nearby potholes by distance within a chosen radius.
- Test generator script: makes N random potholes across Cape Town suburbs through the real upload API.

Why "not a pothole" matters for the model: the detection model was trained on a dataset of pothole images from online, which weren't taken from the same perspective as our grille-mounted camera (low down, close to the road, looking forward). It's good enough to detect potholes, but it will get some wrong, e.g. manhole covers, shadows or old patches. Every time a crew (or admin) marks something as "not a pothole", we get the original detection image, taken by our actual camera from our actual perspective, labelled as a false positive with a reason for what it really was. On the flip side, every pothole marked filled is a crew-confirmed real pothole, with its detection image from the same camera. Over time this builds a labelled dataset from the real deployment for free, as a side effect of the repair work, with no one having to label images by hand. That can be used to retrain or fine-tune the model so it improves the more the system is used. The reasons also show which mistakes are most common (e.g. if most false positives are manhole covers, add more of those as negative examples), and the ratio of "not a pothole" to filled gives a simple real-world measure of the model's precision that can be compared between model versions. Caveats: crews could label wrongly (admins can review in the history), it only catches false positives and not potholes the model missed (false negatives), and there's no export yet to pull the images and labels out for training (future work, easy to add since the photos and reasons are all kept).

Considered but not built: in-app turn-by-turn navigation (browsers pause when the screen locks, no traffic/rerouting, so hand off to Google Maps; an optimised visiting order with OSRM is possible future work). Failed-repair detection left out as too advanced to test.

Limitations: needs HTTPS for phone GPS and clipboard, default keys must be changed, Flask dev server only, single shared admin key (history can't say which admin), no undo for statuses, share links can't be revoked, assumed asphalt depth.

Tested with scripts against a copy of the database (auth, bad input, duplicates, job creation, share links, crew marking, history, search) and headless browser screenshots at desktop and phone sizes.
